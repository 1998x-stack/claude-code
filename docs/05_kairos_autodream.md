## 一、KAIROS 是什么？从古希腊语说起

**KAIROS**（καιρός）是古希腊语中"**合适时机**"的意思，区别于 Chronos（线性时间），它指的是**质的时间、恰当的时机**。

这个命名不是偶然的——它体现了这个功能的核心理念：AI 不应该只在用户召唤时才工作，而应该在**合适的时机**主动行动。

泄露代码显示，KAIROS 在整个 Claude Code 代码库中被引用超过 **150 次**，由 `PROACTIVE` 和 `KAIROS` 两个编译时 Feature Flag 控制，在外部发布版本中完全不可见。

这是迄今为止泄露内容中**最具战略意义的产品路线图**揭示。

## 二、KAIROS 的核心特性

### 2.1 常驻守护进程模式

KAIROS 将 Claude Code 从一个"被动响应"工具变成一个"**主动运作**"的 Agent：

```
传统模式（当前已发布）：
用户输入 ──→ Claude 响应 ──→ 等待下一个输入（休眠）

KAIROS 模式（未发布）：
┌─────────────────────────────────────────────────────┐
│                   KAIROS 守护进程                    │
│                                                     │
│  [5分钟定时器]───→ 接收 <tick> 信号                  │
│       ↑                    │                        │
│       │                    ▼                        │
│    等待下一次        分析当前状态                      │
│    tick             (文件变化？新提交？空闲？)          │
│                            │                        │
│                            ▼                        │
│                    决定是否主动行动                    │
│                    (代码审查？记忆整合？警报？)         │
│                            │                        │
│                    行动 or 继续监控                   │
└─────────────────────────────────────────────────────┘
```

### 2.2 append-only 日志系统

KAIROS 维护**按天追加的日志文件**，记录：

```
~/.claude/kairos/
├── 2026-03-31.log    # 今天的日志
├── 2026-03-30.log    # 昨天的日志
└── ...
```

日志内容包括：
- **Observations**（观察）：Agent 注意到的事情
- **Decisions**（决策）：Agent 做出的决定
- **Actions**（行动）：Agent 执行的操作
- **Hypotheses**（假设）：Agent 形成的待验证假设

这些日志是 AutoDream 系统的原材料。

### 2.3 Brief 输出模式：克制的主动性

当 KAIROS 需要向用户报告时，它使用一种特殊的输出格式：**Brief Mode**（简洁模式）。

设计理念：一个常驻助手不应该像主动对话模式那样详细，它只在**有真正价值的信息**时才发言，且表达极度简洁，不打扰用户工作流。

类比：这就像从"聊天的朋友"到"专业助手"的区别——只在有重要信息时才发声。

### 2.4 KAIROS 专属工具

KAIROS 拥有一些普通 Claude Code 会话没有的额外工具：

| 工具名 | 功能 |
|---|---|
| `FileWatchTool` | 监控文件系统变化 |
| `GitWebhookTool` | 订阅 Git 仓库事件 |
| `DreamTool` | 触发记忆整合（/dream 命令）|
| `CronScheduler` | 定时任务调度 |
| `BackgroundBashTool` | 后台执行长时间命令 |

## 三、AutoDream：AI 的"睡眠记忆整合"

### 3.1 生物学灵感

AutoDream 的灵感来自人类睡眠时的记忆整合机制：

> 人类在快速眼动睡眠（REM Sleep）中，大脑会回放、整合和巩固白天的记忆，去除不重要的细节，强化关键知识，解决之前的认知矛盾。

AutoDream 试图为 AI Agent 复刻这个过程。

### 3.2 AutoDream 的工作流程

`services/autoDream/` 目录实现了这个背景记忆整合引擎：

```
用户闲置超过阈值（N 分钟）
            │
            ▼
┌──────────────────────────────────────────────────┐
│                  AutoDream 启动                   │
│                                                  │
│  1. Fork 一个独立的子 Agent                       │
│     （与主 Agent 上下文完全隔离）                  │
└──────────────────────────────────────────────────┘
            │
            ▼
┌──────────────────────────────────────────────────┐
│              读取今日 KAIROS 日志                  │
│  + 当前所有 MEMORY.md topic files                │
└──────────────────────────────────────────────────┘
            │
            ▼
┌──────────────────────────────────────────────────┐
│                  整合处理                         │
│                                                  │
│  · 合并相关的分散观察                              │
│  · 检测并解决逻辑矛盾                              │
│  · 将 tentative observations 升华为 verified facts│
│  · 识别新出现的模式                                │
│  · 删除过时或冗余信息                              │
└──────────────────────────────────────────────────┘
            │
            ▼
┌──────────────────────────────────────────────────┐
│               更新记忆文件                        │
│                                                  │
│  · 更新 topic files（新事实、删除旧信息）           │
│  · 更新 MEMORY.md 索引（时间戳、指针）              │
│  · 归档今日日志                                    │
└──────────────────────────────────────────────────┘
            │
            ▼
         完成，主 Agent 恢复
```

### 3.3 为什么要 Fork 子 Agent？

这是一个精妙的工程决策：AutoDream 运行在一个**完全隔离的子 Agent**中，而不是在主 Agent 内部进行。

**原因：**
- **防止"思路污染"**：AutoDream 的整合过程可能引入大量临时的、中间状态的信息。如果在主 Agent 上下文中运行，这些临时信息会干扰主 Agent 的"思路"
- **原子性**：整合结果要么完全成功（写入文件），要么完全不影响（子 Agent 失败，不更新任何文件）
- **独立失败**：子 Agent 崩溃不影响用户的主会话

这与 autoCompact 的设计哲学一致：**危险或复杂的操作总是在隔离的子 Agent 中进行**。

### 3.4 矛盾解决算法

记忆整合中最难的问题是：**当两条记忆互相矛盾时，保留哪一条？**

Claude Code 的规则（从代码注释推断）：

```
矛盾解决优先级：
1. 更近的观察 > 更早的观察（时间权重）
2. 多次验证的事实 > 单次观察（频率权重）
3. 显式确认的事实 > 隐式推断（置信度权重）
4. 用户明确说明的 > Agent 自主推断的（来源权重）
```

例如：
- 日志显示"API 返回 401"（上周）vs "API 正常工作"（今天）→ 保留今天的
- "数据库用 PostgreSQL"（单次观察）vs "数据库用 PostgreSQL"（验证 5 次）→ 升格为已验证事实

## 四、GitHub 集成：Webhook 订阅

KAIROS 的一个特别功能是**订阅 GitHub Webhook**，这意味着：

```
GitHub 事件 ──→ Webhook ──→ KAIROS ──→ 主动行动

示例场景：
- 有人在你的 PR 上留了评论 → KAIROS 主动分析评论并在用户回来时摘要
- CI/CD 流水线失败 → KAIROS 分析失败原因并准备修复建议
- 有新的 Issue 被创建 → KAIROS 检查是否与当前工作相关
- 代码被 merged → KAIROS 更新相关记忆，清理已解决的 TODO
```

这将 Claude Code 从"本地 CLI 工具"升级为"连接开发生态系统的 Agent"。

## 五、ULTRAPLAN：KAIROS 生态的云端扩展

在 KAIROS 相关代码中，还有一个名为 **ULTRAPLAN** 的功能值得专门介绍。

### 5.1 ULTRAPLAN 的工作原理

ULTRAPLAN 是一个将复杂规划任务**外包给远程强力算力**的系统：

```
本地 Claude Code
        │
        │ "这个任务太复杂了，需要 ULTRAPLAN"
        ▼
┌───────────────────────────────────────┐
│    Cloud Container Runtime (CCR)      │
│                                       │
│  运行：Claude Opus 4.6 (Fennec)       │
│  时间：最长 30 分钟                    │
│  任务：复杂架构规划、大规模重构方案     │
└───────────────────────────────────────┘
        │
        │ 生成规划结果
        ▼
浏览器弹出确认对话框
（用户审查 30 分钟深度思考的结果）
        │
        │ 用户批准
        ▼
特殊 Sentinel 值：__ULTRAPLAN_TELEPORT_LOCAL__
（将结果"传送"回本地终端）
        │
        ▼
本地 Claude Code 继续执行
```

### 5.2 "传送"机制

`__ULTRAPLAN_TELEPORT_LOCAL__` 这个哨兵值的存在说明 Anthropic 设计了一种优雅的本地/云端状态同步机制：

当浏览器中的用户批准了 ULTRAPLAN 结果，系统会在本地 Terminal 中注入这个哨兵值，让本地 Agent "感知到"云端任务已完成并获取结果。

这个设计的优雅之处在于：从 Agent 的视角来看，这只是一个普通的工具调用返回值；但实际上，这个值触发了一个跨越本地-云端-浏览器的状态同步流程。

## 六、/dream 斜杠命令

用户也可以手动触发记忆整合，通过 `/dream` 命令：

```bash
/dream
```

这会立即启动 AutoDream 子 Agent，进行显式的记忆整合。

这个命令特别适合：
- 长时间工作后，手动"总结今天的学习"
- 在切换项目前，整合当前项目的知识
- 感觉 Agent 开始"混乱"时，主动清理记忆

## 七、KAIROS 的隐私考量

常驻监控 Agent 天然引发隐私问题：

### 7.1 KAIROS 监控什么？

从代码推断，KAIROS 监控：
- **文件系统变化**（如 Git 提交、文件修改）
- **GitHub Webhook 事件**
- **用户活跃/闲置状态**（判断是否运行 AutoDream）

### 7.2 KAIROS 不监控什么？

值得注意的是，代码中的遥测系统（下一篇将详细讲解）明确说明**不会记录完整的对话内容或代码内容**。KAIROS 作为一个更"深度监控"的系统，其隐私边界的设计细节目前还不完全清楚。

这是一个未发布功能，也许正是出于隐私问题的考虑，Anthropic 还在谨慎打磨。

## 九、工程洞见：从被动到主动的 Agent 范式转变

KAIROS 代表了 AI Agent 的下一个进化阶段：

### 阶段一：被动问答（ChatGPT 范式）
用户问 → AI 答 → 等待

### 阶段二：主动执行（Claude Code 当前版本）
用户请求 → AI 规划 → AI 执行 → 等待下一个请求

### 阶段三：自主守护（KAIROS 范式）
AI 持续监控 → 在合适时机主动行动 → 用户回来时已有积累

这个演进路径让人想起从"静态网页"到"Web App"再到"PWA + 后台同步"的演进。AI Agent 也在从"静态响应"走向"动态感知"。

## 十、小结

KAIROS 和 AutoDream 揭示了 Anthropic 对 AI Agent 未来的愿景：

- **不是工具，而是助手**：持续存在，不需要每次显式召唤
- **不只是执行，还会学习**：通过 AutoDream 不断整合和巩固知识
- **不只是本地，还连接生态**：通过 GitHub Webhook 感知开发生态的变化
- **不只是反应，还会预判**：在合适时机主动提供帮助

当这些功能最终发布时，Claude Code 将从一个"很强的 AI 助手"变成一个"真正的数字团队成员"。
